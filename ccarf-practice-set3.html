Scenario 1 Questions 1–5

Code generation with Claude Code

Your team uses Claude Code to build features in a large existing codebase. You're deciding how it's configured and how developers should work with it.

Q1 Claude Code Configuration & Workflows

The root CLAUDE.md has grown to 900 lines covering testing, API style and deployment. All of it applies across the whole repository. The team wants it easier to maintain, without changing what Claude Code loads. What is the best approach?

  1. Split it into topic files under .claude/commands, which are loaded alongside CLAUDE.md for the whole project
  2. Split it into a CLAUDE.md in each top-level folder, which are all loaded together when a session starts
  3. Split it into topic files under .claude/rules, which are loaded alongside CLAUDE.md for the whole project
  4. Split it into skills under .claude/skills, which are loaded in full alongside CLAUDE.md for the whole project
Show answer
C. Rule files with no path pattern load for the whole project, the same as CLAUDE.md. Commands and skills load only when they're used, and a nested CLAUDE.md loads only when Claude works in that folder.
Q2 Claude Code Configuration & Workflows

A team skill, /audit-deps, runs a long analysis that prints hundreds of lines. After it runs, the main conversation is crowded with its output and later answers get worse. What is the best change to the skill?

  1. Add context: fork to its frontmatter, so it runs in a subagent and returns a summary
  2. Add allowed-tools to its frontmatter, so it runs with fewer tools and prints less output
  3. Move its instructions into CLAUDE.md, so they're loaded once and the output stays shorter
  4. Add an argument-hint to its frontmatter, so developers can ask it for a shorter report
Show answer
A. Forking runs the skill in its own context, so the long output stays out of the main conversation. Limiting tools changes what the skill is allowed to do, not how much it prints.
Q3 Claude Code Configuration & Workflows

A developer wants their own version of the team's review skill with a few extra checks. Teammates shouldn't be affected. What is the best way to set this up?

  1. Edit the team's skill in .claude/skills and commit it, with a note that the extra checks are optional
  2. Create a skill with the same name in .claude/settings.local.json, which is personal and overrides the team's version
  3. Edit the team's skill in .claude/skills locally, and leave the change uncommitted in the working copy
  4. Create a skill with a different name in ~/.claude/skills, which is personal and isn't shared through the repository
Show answer
D. Personal skills live in your home folder and never reach teammates. settings.local.json holds settings, not skills, and an uncommitted edit is easy to commit by accident or to lose.
Q4 Prompt Engineering & Structured Output

A developer is about to ask Claude Code to build a caching layer. They don't know the area well, and the requirements are vague. What is the most effective way to begin?

  1. Ask Claude to implement its best guess first, and correct the design through several rounds of review comments
  2. Ask Claude to interview them about requirements and edge cases first, and implement once the answers are agreed
  3. Ask Claude to implement three different designs in parallel, and keep whichever one passes the most tests
  4. Ask Claude to copy the caching approach from another service, and adjust it wherever the tests fail
Show answer
B. When requirements are unclear, having Claude ask questions first brings out decisions the developer hadn't thought about. Guessing and then correcting spends several rounds undoing the wrong design.
Q5 Claude Code Configuration & Workflows

A developer resumes a Claude Code session from two days ago. Since then, a teammate has changed several of the files that Claude analysed in that session. What should the developer do?

  1. Resume the session and carry on, since the earlier analysis is still held in the conversation history
  2. Resume the session and ask Claude to re-read every file in the repository before it continues
  3. Resume the session and ask Claude to rely on its earlier tool results wherever the files differ
  4. Resume the session and tell Claude which files changed, so that it re-reads those before it continues
Show answer
D. A resumed session still holds the old file contents, which are now out of date for the changed files. Pointing Claude at what changed is much cheaper than re-reading everything.
Scenario 2 Questions 6–10

Structured data extraction

You're designing a system that uses Claude to pull structured data out of documents such as invoices and contracts. The output is checked against a JSON schema and passed to downstream systems. Accuracy has to stay high, including on unusual documents.

Q6 Tool Design & MCP Integration

You've defined three extraction tools, one each for invoices, contracts and receipts. The document type isn't known in advance. Claude usually calls the right tool, but sometimes replies in plain text. What is the best fix?

  1. Set tool_choice to auto, so Claude decides whether to call a tool or reply in text
  2. Set tool_choice to any, so Claude must call a tool but can choose which one fits
  3. Set tool_choice to the invoice tool, so Claude must call it for every document it receives
  4. Set tool_choice to none, so Claude replies in text that follows the schema in the prompt
Show answer
B. any forces a tool call and leaves the choice of tool to Claude. auto still allows a text reply, and naming one tool forces the invoice schema onto contracts and receipts.
Q7 Prompt Engineering & Structured Output

The schema has a category field with a fixed list of allowed values. Some documents have a category that isn't on the list, and Claude picks a poor match. What is the best change to the schema?

  1. Remove the fixed list from the schema, and accept any free-text value for the category
  2. Keep the list as it is, and tell Claude to choose whichever value is closest
  3. Add an "other" value to the list, with a separate text field for the detail
  4. Keep the list as it is, and reject any document whose category isn't on it
Show answer
C. An escape value stops the model forcing a poor fit, and the detail field keeps the real information. Dropping the list loses the consistency that downstream systems rely on.
Q8 Prompt Engineering & Structured Output

Extraction works well on standard invoices. It fails on unusual layouts, such as totals given in a footnote or amounts in two currencies. What is the most effective improvement?

  1. Add a few worked examples to the prompt that cover the unusual layouts and their correct extractions
  2. Add detailed written rules to the prompt that describe each of the unusual layouts seen so far
  3. Add a second extraction pass over every document, and keep whichever result has more fields filled
  4. Add a pre-processing step that converts every document into one standard layout before extraction
Show answer
A. Worked examples show Claude how to handle varied layouts, and it generalises from them better than from a growing list of written rules.
Q9 Context Management & Reliability

You want to send only the doubtful extractions to human review. Which approach gives the most dependable signal for deciding what to send?

  1. Have Claude give a confidence score per document, and trust any document scored above ninety per cent
  2. Have Claude extract each document twice, and trust the result whenever both extractions are identical
  3. Have Claude give a written reason per field, and trust any field that comes with a detailed reason
  4. Have Claude give a confidence score per field, and check those scores against a labelled sample first
Show answer
D. A model's confidence scores are only useful once they've been checked against known answers. Scores per field also show which part of a document needs a look. Two identical extractions can both be wrong in the same way.
Q10 Context Management & Reliability

A validation step sends failed extractions back to Claude with the error. For some invoices it keeps failing on the supplier's tax ID, however many times it retries. Those invoices don't show a tax ID anywhere. What should you change?

  1. Increase the number of retries from three to ten, with the validation error included each time
  2. Retry with a more capable model, and include the validation errors from the earlier attempts
  3. Stop retrying when the value isn't in the document, and return null or send it for review
  4. Retry with a stricter prompt, which says that the tax ID field must always be filled in
Show answer
C. Retrying helps with format and structure errors. It can't produce information the document doesn't contain, and pushing harder invites an invented value.
Scenario 3 Questions 11–15

Multi-agent research system

You're designing a research system in which a coordinator agent hands work to specialised subagents: one searches the web, one analyses documents, one combines the findings and one writes the report. Each subagent runs with its own separate context.

Q11 Agentic Architecture & Orchestration

The coordinator sends every query through all four subagents, including simple factual questions. Simple queries are slow and cost as much as complex ones. What is the best change?

  1. Have the coordinator assess each query, and call only the subagents that the query actually needs
  2. Have the coordinator call every subagent each time, and discard the results it doesn't need
  3. Have the coordinator call every subagent each time, but on a smaller and cheaper model
  4. Have users choose which subagents to run, with a set of checkboxes on the query form
Show answer
A. Not every query needs every specialist. Letting the coordinator choose saves time and cost on simple queries without lowering quality on complex ones.
Q12 Agentic Architecture & Orchestration

In the current design, subagents send messages directly to one another. Failures are hard to trace, and each subagent handles errors in its own way. What is the best redesign?

  1. Keep direct messaging, and add logging inside each subagent for every message that it sends
  2. Route all communication through the coordinator, so there is one place for control and error handling
  3. Keep direct messaging, and add a shared memory file that every subagent reads and writes
  4. Route all communication through the report writer, so the final step sees everything first
Show answer
B. With one hub, every handoff is visible and errors are handled the same way each time. Logging lets you see the tangle but doesn't remove it.
Q13 Agentic Architecture & Orchestration

The search subagent returns about 15,000 tokens of raw page content and its own reasoning. The coordinator passes all of it to the synthesis subagent, whose output has become less focused. What should the search subagent return?

  1. Everything it gathered, with the synthesis subagent moved to a model with a larger context
  2. A one-sentence conclusion for each question, leaving out the sources and the supporting detail
  3. Everything it gathered, with the coordinator cutting it down to a fixed length afterwards
  4. Structured key findings with their sources, leaving out the raw pages and its own reasoning
Show answer
D. The next agent needs the findings and where they came from, not the raw pages. A single sentence loses the sources that the report has to cite.
Q14 Tool Design & MCP Integration

The search subagent has one general fetch tool. Flags on it switch between searching, loading a page and reading a PDF, and the subagent often sets the wrong flags. What is the best fix?

  1. Keep the single tool, and add a longer description that explains every flag in detail
  2. Keep the single tool, and add examples of each flag combination to the system prompt
  3. Split it into separate tools for searching, loading pages and reading PDFs, each clearly described
  4. Split the work across three separate subagents, and give each of them the same single tool
Show answer
C. One tool per job, with a clear name and description, is easier for the model to choose correctly than one tool with many flags. Extra subagents add overhead without fixing the tool.
Q15 Context Management & Reliability

For one of five subtopics the search subagent found no usable sources. The final report simply leaves that subtopic out, and readers assume the report is complete. What is the best change?

  1. Have the report state which subtopics lacked sources, so readers know where its coverage is thin
  2. Have the report leave the subtopic out, so that every statement in it is fully sourced
  3. Have the report cover the subtopic from the model's general knowledge, in the same style
  4. Have the system re-run the whole research task until every subtopic has at least one source
Show answer
A. Saying where coverage is thin lets readers judge the report. Leaving the subtopic out hides the gap, and unsourced general knowledge looks the same as researched findings.
