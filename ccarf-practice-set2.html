Scenario 1 Questions 1–5

Code generation with Claude Code

Your team uses Claude Code to build features in a large existing codebase. You're deciding how it's configured and how developers should work with it.

Q1 Claude Code Configuration & Workflows

A developer wants Claude Code to restructure the payments module. The change touches about 30 files, and there are several reasonable ways to do it. What is the best way to start?

  1. Start in plan mode, so Claude explores the code and proposes an approach for review before any file is changed
  2. Start with direct edits, so Claude changes files right away and the developer fixes any problems in review afterwards
  3. Split the work by file, and ask Claude to edit each one in a separate session with no shared plan
  4. Ask Claude to rewrite the module from scratch in a new folder, and swap it in once the tests pass
Show answer
A. Large changes with more than one possible design are what plan mode is for: agree the approach before anything is edited. Direct edits (B) suit small, well-defined changes.
Q2 Claude Code Configuration & Workflows

Test files sit next to the source files throughout the repository (*.test.ts) and follow different conventions from the source code. Claude Code keeps applying the source conventions to tests. What is the best configuration?

  1. Put the test conventions in a CLAUDE.md inside every folder that contains test files across the repository
  2. Add the test conventions to the root CLAUDE.md, under a heading that says they apply only to tests
  3. Create a rule file under .claude/rules with the path pattern **/*.test.ts, so it loads for those files only
  4. Put the test conventions in each developer's personal CLAUDE.md, so they apply in every project they open
Show answer
C. Path-scoped rules apply by file pattern, which fits files spread across many folders. Folder-level files (A) would have to be repeated everywhere, and a heading in the root file (B) is loaded for everything.
Q3 Claude Code Configuration & Workflows

The team wants a shared /review command that every developer gets automatically when they clone the repository. Where should it be defined?

  1. In ~/.claude/commands on each developer's machine, set up by hand when they join the team
  2. In .claude/commands inside the repository, committed to version control so everyone gets it on clone
  3. In the root CLAUDE.md, as a section that describes the steps the command should follow
  4. In .claude/settings.local.json in the repository, listed under a custom commands entry for the team
Show answer
B. Project commands live in the repository's .claude/commands folder and are shared through version control. The home-folder location (A) is personal, and settings.local.json (D) is for personal, uncommitted settings.
Q4 Agentic Architecture & Orchestration

Before implementing a feature, a developer asks Claude Code to work out how authentication flows through the codebase. The main session fills up with file contents, and the quality of the later coding work drops. What is the best approach?

  1. Hand the investigation to a subagent that explores in its own context and returns a short summary
  2. Ask Claude to read every relevant file in the main session first, then clear the conversation before it starts coding
  3. Raise the output token limit for the main session, so it has more room for the files it reads
  4. Tell Claude to read only the first fifty lines of each file, so that less context is used
Show answer
A. A subagent does the reading in a separate context and passes back only the conclusions. Clearing the conversation (B) throws away the findings along with the clutter.
Q5 Prompt Engineering & Structured Output

Claude has generated a data-transformation function. The developer has described the requirements in prose twice, and it still gets the same edge cases wrong (empty values and mixed date formats). What is the most effective next step?

  1. Rewrite the description a third time, with more emphasis on the edge cases that are still being missed
  2. Ask Claude to think harder about the edge cases, and to check its own work before it responds
  3. Switch to a more capable model, and submit the same written description of the requirements once more
  4. Give two or three concrete input and expected-output examples, or failing tests, that cover those edge cases
Show answer
D. When prose has failed twice, concrete examples or tests remove the ambiguity. They also give Claude something to run and check against.
Scenario 2 Questions 6–10

Developer productivity with Claude

You're building an internal assistant with the Claude Agent SDK. It helps engineers explore unfamiliar codebases, understand legacy systems and automate routine tasks. It uses the built-in tools (Read, Grep, Glob, Bash) and connects to MCP servers.

Q6 Tool Design & MCP Integration

The agent needs to find every place the function processRefund is called across the repository. Which approach should it take?

  1. Use Glob with a pattern that matches the function name across every source folder in the repository
  2. Use Grep to search file contents for the function name, then Read the files that matter most
  3. Use Read on each source file in turn, and look for the function name in the returned text
  4. Use Bash to print every file to the terminal, and scan the combined output for the name
Show answer
B. Grep searches inside files, and Glob matches file names and paths. Reading every file (C, D) works but fills the context with content that isn't needed.
Q7 Tool Design & MCP Integration

The team shares an MCP server for the issue tracker. Every developer should get it automatically, and each one has their own API token. How should it be configured?

  1. Add the server to each developer's user-level configuration, with their own token written into that file
  2. Commit the server to the project's .mcp.json, with every developer's token listed in the same file
  3. Commit the server to the project's .mcp.json, and reference the token through an environment variable
  4. Hard-code one shared team token in the server's source code, and commit that to the repository
Show answer
C. The project file shares the server definition, and the environment variable keeps each person's token out of version control. User-level configuration (A) works but has to be set up by hand for every developer.
Q8 Agentic Architecture & Orchestration

You're writing the agent's main loop directly against the API. How should the loop decide when the task is finished?

  1. Stop when the response's stop_reason is end_turn, and keep going while it is tool_use
  2. Stop when the assistant's text contains a phrase such as "task complete" or "I'm done"
  3. Stop after a fixed number of turns, whatever the response's stop_reason or content says
  4. Stop when a response contains any text block, and keep going while it contains none
Show answer
A. stop_reason is the reliable signal. Claude often writes text alongside a tool call, so D ends too early, and a fixed turn count (C) is only useful as a safety limit on top.
Q9 Context Management & Reliability

During a long session exploring a legacy system, the agent's answers become vague. It talks about "typical patterns" where earlier it named the specific classes it had found. What is the best fix?

  1. Have the agent re-read every file it opened earlier, each time the user asks a new question
  2. Have the agent answer from general knowledge of the framework when earlier findings have dropped out of context
  3. Have the user restate the important findings at the start of each new question they ask
  4. Have the agent record key findings in a notes file, and re-read it after context is compacted
Show answer
D. Specific findings are lost when a long history is compressed. A notes file keeps them outside the conversation, where the agent can reload them.
Q10 Agentic Architecture & Orchestration

Yesterday a developer used the assistant to analyse a module in depth. Today they want to try two different refactoring approaches, both starting from that analysis. What is the best way to set this up?

  1. Start two new sessions, and ask each one to redo the analysis before trying its approach
  2. Resume yesterday's session, and try both approaches one after the other in the same conversation
  3. Fork yesterday's session into two branches, so each approach starts from the same analysis
  4. Paste a summary of yesterday's analysis into two new sessions, and try one approach in each
Show answer
C. Forking keeps the full analysis and gives each approach its own branch. Trying both in one conversation (B) lets the first attempt influence the second.
Scenario 3 Questions 11–15

Structured data extraction

You're designing a system that uses Claude to pull structured data out of documents such as invoices and contracts. The output is checked against a JSON schema and passed to downstream systems. Accuracy has to stay high, including on unusual documents.

Q11 Prompt Engineering & Structured Output

Downstream systems need every extraction to match the JSON schema exactly. Which approach gives the strongest guarantee about the structure of the output?

  1. Describe the JSON format in detail in the prompt, and ask Claude to follow it exactly
  2. Define the schema as a tool's input schema, and require Claude to call that tool
  3. Give three example outputs in the prompt, and ask Claude to match their structure
  4. Ask for JSON in the prompt, and run a repair step on anything that fails to parse
Show answer
B. Requiring a tool call with a defined input schema constrains the structure of the output. Instructions and examples (A, C) improve the odds but don't guarantee it.
Q12 Prompt Engineering & Structured Output

Some invoices have no purchase order number. The schema marks that field as required, and Claude sometimes fills it with an invented number. What is the best fix?

  1. Add an instruction that tells Claude never to invent values for fields it can't find
  2. Keep the field required, and have reviewers check the purchase order number on every invoice
  3. Make the field nullable in the schema, so Claude can return null when no value exists
  4. Remove the field from the schema, and collect purchase order numbers through a separate manual process
Show answer
C. A required field with no way to say "not present" pushes the model to fill it with something. Allowing null gives it an honest answer to return.
Q13 Prompt Engineering & Structured Output

An extraction passes schema validation, but its line items don't add up to the invoice total. What is the best way to handle this?

  1. Send the document back with the failed extraction and the mismatch, and ask for a correction
  2. Send the same request again unchanged, up to three times, until the totals happen to match
  3. Tighten the JSON schema with stricter types, so that mismatched totals are rejected as invalid
  4. Accept the extraction as it is, and let the downstream finance system catch the mismatch later
Show answer
A. A schema checks structure, not whether the numbers make sense, so this needs a check in code. Retrying with the specific error gives Claude what it needs to correct it, which a blind retry (B) doesn't.
Q14 Context Management & Reliability

Overall extraction accuracy is 97%, and the business wants to cut the amount of human review. What should you do before reducing it?

  1. Review a random five per cent of all extractions, and send everything else straight through automatically
  2. Stop human review altogether, since overall accuracy is already above the target the business agreed
  3. Review only the documents where Claude says in its output that it found the task difficult
  4. Check accuracy by document type and field, then send the weaker categories to human review
Show answer
D. An overall figure can hide a document type or field that performs badly. Measure by segment, then keep review where the errors actually are.
Q15 Context Management & Reliability

You send 10,000 archived contracts through the Message Batches API. 300 requests fail because the documents are too long. What is the best way to handle the failures?

  1. Resubmit the whole batch of ten thousand, with a higher output token limit set on every request
  2. Find the failed requests by their custom IDs, split those documents into parts, and resubmit only those
  3. Drop the three hundred failed documents, since ninety-seven per cent of the batch came back fine
  4. Move all ten thousand documents to real-time calls, so that failures can be seen as they happen
Show answer
B. The custom ID on each request tells you exactly which documents failed. Fix those and resubmit them alone, without paying again for the 9,700 that worked.
