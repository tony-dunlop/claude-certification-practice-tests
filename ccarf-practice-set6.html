Scenario 1 Questions 1–5

Multi-agent research system

You're designing a research system in which a coordinator agent hands work to specialised subagents: one searches the web, one analyses documents, one combines the findings and one writes the report. Each subagent runs with its own separate context.

Q1 Agentic Architecture & Orchestration

Research questions arrive as four to six sub-questions. The sub-questions don't depend on one another, but the report can't be written until all of them are answered and any conflicts between them are settled. Today a single agent works through everything in one context. A run takes 25 minutes, and the later sub-questions get thinner treatment as the context fills. You need to cut the run time, keep the treatment even, and keep one place that decides whether coverage is good enough. Which structure fits best?

  1. Use a coordinator that sends each sub-question to its own subagent one after another, collects the findings, checks coverage itself, and only then passes the combined findings on to the synthesis step.
  2. Use a chain in which each sub-question's subagent passes its findings directly to the next subagent, with the last one in the chain checking coverage and then writing the synthesis itself.
  3. Use a coordinator that sends each sub-question to its own subagent in parallel, collects the findings, checks coverage itself, and only then passes the combined findings on to the synthesis step.
  4. Use parallel subagents for the sub-questions with no coordinator, have each one write its own section of the report, and join the sections in the order the sub-questions were asked.
Show answer
C. Independent sub-questions can run in parallel, which cuts the run time and gives each one a clean context. The coordinator stays the single place that judges coverage. Running them one after another keeps the control but not the speed, and dropping the coordinator loses the coverage check and the settling of conflicts.
Q2 Agentic Architecture & Orchestration

The coordinator briefs the document-analysis subagent with a step list: open each PDF, extract every table, and list every figure above ten per cent. This works on standard reports. On unusual ones, where the key data sits in the narrative text and there are no tables, the subagent returns almost nothing. The coordinator also needs to compare results across documents, so it must be able to line them up. Which change to the brief best addresses both needs?

  1. State what the analysis is for and what a good result contains, let the subagent decide how to find it in each document, and require every result in the same fixed structure.
  2. State what the analysis is for and what a good result contains, let the subagent decide how to find it in each document, and let it choose whichever structure suits each result.
  3. Keep the step list, add further steps that cover narrative text and documents with no tables, and require every result in the same fixed structure so that documents can be compared.
  4. Keep the step list, add a closing step telling the subagent to use its judgement when a document doesn't fit, and let it choose whichever structure suits each result.
Show answer
A. A goal with success criteria lets the subagent adapt to documents the step list never anticipated. A fixed return structure keeps the results comparable, so the coordinator keeps its view. Adding steps only covers the cases someone thought of in advance.
Q3 Tool Design & MCP Integration

All four subagents were given the full set of 14 tools "for flexibility". Logs show the report writer occasionally running new web searches and adding claims that never went through analysis or synthesis, and the search subagent sometimes writing files. A teammate points out that it is occasionally handy for the report writer to look something up. You want every claim in a report to have passed through the same checks. What is the best design?

  1. Give each subagent only the tools for its own role, except for the report writer, which keeps the search tools so that it can fill small gaps without a round trip.
  2. Keep all the tools on every subagent, and add a section to each system prompt that lists which tools belong to its role and which ones it should leave alone.
  3. Keep all the tools on every subagent, and have the coordinator inspect each subagent's tool calls afterwards and discard any output that came from a tool outside its role.
  4. Give each subagent only the tools for its own role, and send any need outside that role back through the coordinator, so that new material always passes through analysis and synthesis.
Show answer
D. Tools that aren't offered can't be misused, and fewer tools make each subagent's choices more reliable. Sending out-of-role needs back through the coordinator keeps every claim on the same path. Leaving the report writer its search tools keeps the exact problem you are trying to remove.
Q4 Agentic Architecture & Orchestration

The coordinator calls the synthesis subagent with a prose summary of what the search and analysis subagents found. The synthesis comes back with claims that have no sources, and the subagent often has to ask the coordinator for details that were left out, which costs extra round trips. What should the coordinator pass in so that the synthesis subagent can finish the task in one go?

  1. The findings themselves as structured data, each with its source, date and supporting quote, but without the research question, so that the synthesis is not steered towards one particular answer.
  2. The findings themselves as structured data, each with its source, date and supporting quote, together with the research question and the output format that the report writer expects to receive.
  3. A longer prose summary of the findings that mentions the main sources by name, together with the research question and the output format that the report writer expects to receive.
  4. The identifiers of the earlier subagent runs, together with the research question, so that the synthesis subagent can ask the coordinator for the particular findings it decides that it needs.
Show answer
B. A subagent has only what its brief contains. To finish in one go it needs the findings with their source details, the question they answer and the format wanted. A summary, however long, has already thrown the source details away.
Q5 Agentic Architecture & Orchestration

One kind of request asks the system to compare how three countries regulate a product, then assess which approach would suit a fourth country. The three country studies don't depend on one another. The assessment depends on all three. Today the coordinator starts all four tasks at once, and the assessment comes back generic because its subagent started with nothing to assess. How should the coordinator order the work?

  1. Run the three country studies in parallel, wait until all three have returned, and then start the assessment with their findings included in the brief that its subagent is given.
  2. Run all four tasks in parallel as now, and have the assessment subagent ask the coordinator for the country findings when it reaches the point where it needs them.
  3. Run all four tasks one after another with the assessment last, so that each subagent can be given the findings of every task that finished before it started.
  4. Run the three country studies in parallel, start the assessment at the same moment, and combine the assessment with the country findings afterwards in the synthesis step.
Show answer
A. Run independent work in parallel and dependent work after the things it depends on. Running everything in sequence would also work, but it gives up the time saved on the three studies.
Scenario 2 Questions 6–10

Code generation with Claude Code

Your team uses Claude Code to build features in a large existing codebase. You're deciding how it's configured and how developers should work with it.

Q6 Claude Code Configuration & Workflows

The team has four kinds of guidance to set up. First, coding conventions that apply to every file. Second, rules for API handlers that matter only for files under src/api. Third, a forty-step release procedure that is used about once a fortnight. Fourth, a requirement that the linter runs after every edit, with no exceptions. Which arrangement puts each one in the right place?

  1. Conventions in the project CLAUDE.md, the API rules in a rule file with a path pattern for src/api, the release procedure as a hook, and the linter as a skill.
  2. Conventions in the project CLAUDE.md, the API rules in that same file under their own heading, the release procedure as a skill, and the linter as an instruction in a rule file.
  3. Conventions in a rule file with a path pattern for src/api, the API rules in the project CLAUDE.md, the release procedure as a skill, and the linter as a hook.
  4. Conventions in the project CLAUDE.md, the API rules in a rule file with a path pattern for src/api, the release procedure as a skill, and the linter as a hook.
Show answer
D. Match each mechanism to when the guidance should apply: CLAUDE.md for always, a path-scoped rule for certain files, a skill for an occasional procedure loaded on demand, and a hook for something that must run every time.
Q7 Claude Code Configuration & Workflows

Security policy says Claude Code must never read files in the secrets folder and must never run terraform apply. The restriction has to apply to everyone who works in the repository, and it must not depend on Claude choosing to comply. Where should it be defined?

  1. As deny rules in the permissions of .claude/settings.local.json, which is kept out of version control and applies on the machine where it was written.
  2. As deny rules in the permissions of the project's .claude/settings.json, which is committed and applies to everyone who works in the repository.
  3. As a security section in the project's CLAUDE.md, which is committed and is loaded into every session for everyone who works in the repository.
  4. As a rule file with a path pattern for the secrets folder, which is committed and is loaded whenever Claude works on a matching file.
Show answer
B. Permission rules in settings are enforced by Claude Code itself, so they don't rely on the model complying. The project settings file is shared through the repository. CLAUDE.md and rule files are guidance, which is followed most of the time, not always.
Q8 Claude Code Configuration & Workflows

Yesterday a developer spent a long Claude Code session mapping a module of about forty files and agreeing a refactoring plan. Overnight a teammate merged changes to three of those files. Today the developer wants to carry on and implement the plan. They want to keep the analysis and the agreed plan, avoid acting on file contents that are out of date, and avoid repeating yesterday's work. What should they do?

  1. Resume yesterday's session, and ask Claude to re-read all forty files and rebuild its analysis before it goes any further, so that nothing in the conversation is out of date.
  2. Start a new session, and ask Claude to map the module again from the beginning, so that both the analysis and the plan are based on the files as they are now.
  3. Resume yesterday's session, tell Claude which three files have changed, and ask it to re-read those and confirm that the plan still holds before it goes any further.
  4. Resume yesterday's session and carry on with the plan as agreed, since the earlier file contents are still in the conversation and only three of the files were touched.
Show answer
C. Resuming keeps the analysis and the plan. Pointing Claude at the three changed files refreshes exactly what is stale. Re-reading everything, or starting again, repeats work that is still valid.
Q9 Context Management & Reliability

Claude Code is tracing a data flow through about two hundred files of a legacy system over a session lasting several hours. Many files are more than two thousand lines long. After the context is compacted, Claude can no longer say which functions it had already confirmed, and it starts re-reading files. What combination of habits best keeps a session like this coherent?

  1. Have Claude record confirmed findings in a notes file as it goes, read only the relevant part of each file, and hand broad searches to subagents that return short summaries.
  2. Have Claude record confirmed findings in a notes file as it goes, and keep reading each file in full from top to bottom, so that nothing relevant in a file is missed.
  3. Have Claude rely on the summary that is made when the context is compacted, read only the relevant part of each file, and hand broad searches to subagents that return short summaries.
  4. Have Claude rely on the summary that is made when the context is compacted, and start a fresh session whenever its answers turn vague, repeating the trace from the entry point.
Show answer
A. Three habits work together: a notes file keeps exact findings outside the conversation, targeted reading slows the rate at which context fills, and subagents keep broad searches out of the main context. A compaction summary loses the specifics that a long trace depends on.
Q10 Tool Design & MCP Integration

For one task Claude needs to do four things: find every file in the repository whose name ends in .migration.sql, find every place where the function applyDiscount is called, understand the code of the two most relevant callers, and check which migrations have been applied by running the project's status command. Which choice of built-in tools is best?

  1. Grep for the migration files, Glob for the calls to the function, Read for the two callers, and Bash for the project's status command.
  2. Glob for the migration files, Grep for the calls to the function, Bash with cat for the two callers, and Read for the project's status command.
  3. Glob for the migration files, Grep for the calls to the function, Read for the two callers, and Bash for the project's status command.
  4. Bash with find for the migration files, Bash with grep for the calls, Read for the two callers, and Bash for the project's status command.
Show answer
C. Glob matches file names and paths, Grep searches inside files, Read loads a file's contents, and Bash runs commands. Shell commands can do the first two jobs as well, but the dedicated tools are the intended choice and return results in a form Claude handles better.
Scenario 3 Questions 11–15

Claude Code for continuous integration

Your team is adding Claude Code to its CI pipeline. On every pull request it reviews the changes and posts comments, and a nightly job generates missing tests.

Q11 Claude Code Configuration & Workflows

You're setting up the pull request review job. Reviews have to apply the team's standards, the job must not be able to change code or push anything, and a script will post each finding as an inline comment on the right line. Today the job runs with the default tools, the standards were pasted into the job's prompt months ago and have drifted from the repository's own, and the output is prose. Which configuration meets all three needs?

  1. Load the standards from the project's CLAUDE.md, leave the default tools in place for simple fixes, and require the findings as JSON with a file, line, severity and message for each one.
  2. Load the standards from the project's CLAUDE.md, limit the job to read-only tools, and require the findings as JSON with a file, line, severity and message for each one.
  3. Keep the standards in the job's own prompt, limit the job to read-only tools, and require the findings as JSON with a file, line, severity and message for each one.
  4. Load the standards from the project's CLAUDE.md, limit the job to read-only tools, and ask for the findings as a Markdown list that the script can then split up into comments.
Show answer
B. Each part answers one need: the project file is the single maintained copy of the standards, read-only tools mean the job can't change or push anything, and structured output is what a script can post reliably.
Q12 Claude Code Configuration & Workflows

In the nightly job, one Claude Code run generates the missing tests and a second step reviews them. The review step currently resumes the generating session and asks it to review its own changes. It approves almost everything. You want a review that judges the tests on their merits and still applies the team's standards. Which design is best?

  1. Run the review as a new session that receives the changes, the project's standards and the generating session's full conversation, so that it understands the reasoning behind every decision.
  2. Run the review by resuming the generating session with the project's standards added and an instruction to be critical, so that it has the full background close to hand.
  3. Run the review by resuming the generating session twice, and keep only the findings that turn up in both passes, so that the result is more dependable than one pass.
  4. Run the review as a new session that receives the changes and the project's standards, without the generating session's conversation, so that it judges the tests on what was actually written.
Show answer
D. A session that made the decisions tends to agree with them, and so does a new session that is handed the same reasoning. A fresh session with only the changes and the standards judges the result on its own.
Q13 Claude Code Configuration & Workflows

Test conventions live in three places: general ones in the project's CLAUDE.md, a path-scoped rule file for the tests folder, and fixture naming conventions in the lead developer's personal CLAUDE.md. The nightly test job follows the first two but not the fixture naming. The fix has to reach the CI job and every developer, and the conventions only matter when test files are involved. Where should the fixture naming conventions go?

  1. Into the path-scoped rule file for the tests folder, which is committed with the repository and is loaded only when test files are involved.
  2. Into the project's CLAUDE.md, which is committed with the repository and is loaded into every session, whichever files are involved.
  3. Onto the CI runner, as a copy of the lead developer's personal CLAUDE.md, so that the job loads the same conventions as that developer's sessions.
  4. Into a skill in the repository, which is committed with it and is loaded when a developer or the job decides to invoke it.
Show answer
A. The conventions must be shared, so they belong in the repository, and they matter only for tests, so a path-scoped rule fits exactly. The project CLAUDE.md would also reach everyone, but it would load them into every session.
Q14 Context Management & Reliability

A pull request touching thirty files has had its first review. The developer then pushes two more commits that change four of those files. The second review should check whether the earlier findings were fixed, review the new changes, avoid repeating findings that are already resolved, and keep the cost down. Which approach is best?

  1. Resume the first review's session, and ask it to review all thirty files again from the start, so that the earlier findings and the new changes are covered in a single pass.
  2. Start a new session with the pull request's full set of changes and no record of the first review, so that the second review is not influenced by the first one.
  3. Resume the first review's session, give it the list of files changed since then, and ask it to re-check its earlier findings on those files and review only the new changes.
  4. Start a new session with only the two new commits and no record of the first review, so that just the latest changes are reviewed and the cost stays low.
Show answer
C. The resumed session already knows what it found. Telling it which files changed lets it confirm fixes and look only at what is new. A new session with no record can't tell a fixed finding from one that was never raised.
Q15 Context Management & Reliability

A pull request changes the function calculateTax. Before commenting, the review job needs to understand what else in a large repository could be affected, and it has a limit on the number of turns it can use. Which exploration strategy is best?

  1. Grep for the function's name to find its callers, Read each matching file in full from top to bottom, and then Read every file that those files import as well.
  2. Grep for the function's name to find its callers, Read only the calling code around each match, and follow any wrapper functions the same way until no new callers appear.
  3. Glob for every source file in the repository, Read them in alphabetical order until the turn limit is close, and report on whichever callers were found up to that point.
  4. Read the changed file in full, and judge the impact from the function's own code and comments, without spending any turns on a search of the rest of the repository.
Show answer
B. Search first, then read only what the search points to, and follow the trail outwards. Reading whole files and their imports spends the turn limit on code that has nothing to do with the change.
