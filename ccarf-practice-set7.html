Scenario 1 Questions 1–5

Customer support resolution agent

You're designing an agent that resolves support tickets for an online retailer. It has tools to look up customers and orders, issue refunds, and escalate to a human. The target is to resolve 80% of tickets at first contact without a person stepping in.

Q1 Tool Design & MCP Integration

Every ticket has to begin with a customer lookup, and a refund must only ever use a customer ID and an order ID that came back from the lookup tools. In testing, the agent sometimes opens with a text reply, and it has twice issued a refund against an order ID that it guessed from the customer's message. Which design closes both gaps?

  1. Name get_customer in tool_choice on the first request and return to auto afterwards, and tell the agent in its prompt that refunds must only use IDs returned by the earlier lookups.
  2. Name get_customer in tool_choice on the first request and return to auto afterwards, and have the refund tool refuse any call whose IDs were not returned by the earlier lookups.
  3. Set tool_choice to any on every request so that a tool is always called, and have the refund tool refuse any call whose IDs were not returned by the earlier lookups.
  4. Name get_customer in tool_choice on every request so that the lookup can never be skipped, and tell the agent in its prompt that refunds must only use verified IDs.
Show answer
B. Two separate guarantees are needed. Naming the tool on the first request fixes the opening step, and going back to auto lets the agent carry on. The check on the IDs has to live in the refund tool's own code, because a prompt instruction makes it likely, not certain.
Q2 Context Management & Reliability

Some support conversations run past sixty turns. Cost per ticket is climbing. When the history is summarised, the agent loses order numbers and refund amounts, and each order lookup adds more than forty fields to the conversation, of which about five are ever used. Which approach keeps answers accurate and brings the cost down?

  1. Keep the key facts in a structured block that is updated and sent with every request, and keep every turn and every tool result in full so that nothing can be lost.
  2. Summarise the whole conversation every twenty turns, with the key facts written into each summary as it is made, and trim each tool result to the fields the agent actually uses.
  3. Keep the most recent twenty turns in full and drop everything that is older than that from the request, and trim each tool result to the fields the agent actually uses.
  4. Keep the key facts in a structured block that is updated and sent with every request, summarise the older turns, and trim each tool result to the fields the agent actually uses.
Show answer
D. Exact values such as order numbers don't survive summarising, so they need their own block outside the part that gets compressed. With that in place, summarising older turns and trimming tool results cuts the cost safely. Keeping everything in full protects accuracy but does nothing about the cost.
Q3 Agentic Architecture & Orchestration

A customer asks about two separate orders in one message. To answer, the agent needs the customer record and the details of each order. The three lookups don't depend on one another. Today the agent makes one lookup per response, so there are three round trips before it can reply, and customers notice the delay. What is the best change?

  1. Let the agent ask for all three lookups in one response, run them at the same time, and return all three results together in the next message before it replies.
  2. Let the agent ask for all three lookups in one response, run them at the same time, and return each result in a separate message so that it can react to each.
  3. Keep one lookup per response, and cut the delay by moving the agent to a smaller and faster model, so that each of the three round trips finishes sooner.
  4. Merge the lookups into one large tool that always returns the customer record and every order on the account, whichever of them the customer's question needs.
Show answer
A. Independent lookups can be requested in a single response and run side by side, which turns three round trips into one. The results for one response go back together in the next message. A tool that always returns everything fills the context with orders nobody asked about.
Q4 Agentic Architecture & Orchestration

For billing disputes the agent follows a fixed six-step checklist. It works through every step even after an early lookup has shown the cause, such as a duplicate charge, and it doesn't follow up on things the checklist never mentions, such as a second account under the same email address. Policy does require some checks, identity verification among them, on every dispute. What is the best redesign?

  1. Have the agent plan its next steps from what each lookup shows, adding or dropping steps as it learns more, including the checks that policy requires when they look unnecessary.
  2. Keep the fixed checklist, and extend it with further steps for duplicate charges and second accounts, so that the cases seen so far are covered in a set order.
  3. Have the agent plan its next steps from what each lookup shows, adding or dropping steps as it learns more, while the checks that policy requires stay enforced in code.
  4. Keep the fixed checklist, and add a last step in which the agent reviews everything it found and decides whether any of the earlier steps ought to be repeated.
Show answer
C. Letting the plan follow the findings handles cases nobody listed in advance and stops wasted steps. The checks that must always happen are a different kind of requirement, so they stay enforced in code where the agent can't drop them.
Q5 Prompt Engineering & Structured Output

The agent answers accurately on orders, refunds and delivery. On questions about consumer law and tax it is wrong about a third of the time, and those wrong answers carry real risk. Management wants to keep automation where it performs well. Which change to the prompt and routing is best?

  1. State which topics the agent handles and which it must hand over, with examples on both sides of the line, and send the excluded topics to a person.
  2. State which topics the agent handles, leave the others unmentioned so that it can still attempt them, and add a note to those answers that they may be wrong.
  3. Tell the agent to answer only when it is confident, with examples of confident answers, and send anything that it marks as uncertain to a person.
  4. Tell the agent to take special care over consumer law and tax, with examples of careful answers, and keep every topic automated in the way that it is now.
Show answer
A. Where performance is unreliable, draw an explicit boundary: say what is in, say what is out, and show examples of each. Relying on the agent's own sense of confidence doesn't work, because it is often confident when it is wrong.
Scenario 2 Questions 6–10

Developer productivity with Claude

You're building an internal assistant with the Claude Agent SDK. It helps engineers explore unfamiliar codebases, understand legacy systems and automate routine tasks. It uses the built-in tools (Read, Edit, Write, Grep, Glob, Bash) and connects to MCP servers.

Q6 Agentic Architecture & Orchestration

You've defined a test-runner subagent with a description, a prompt and a tool list containing Read and Grep. The coordinator delegates test runs to it correctly. Each time, the subagent reads the test files, explains what the tests would probably do, and reports that it has no way to execute them. What is the cause, and the fix?

  1. The coordinator's allowed tools leave out the tool that starts subagents, so the work never reaches the subagent, and that tool needs to be added to the coordinator.
  2. The subagent's description is too brief for the coordinator to match tasks to it, so the wrong work is delegated, and the description needs to be rewritten.
  3. The subagent's definition lists only Read and Grep as its tools, so it has no way to run commands, and Bash needs to be added to that list.
  4. The subagent's prompt doesn't mention running the tests, so it doesn't know that it should, and an instruction to run them needs to be added to it.
Show answer
C. The symptoms locate the fault. Delegation works, so the coordinator and the description are fine. The subagent wants to run the tests and says it can't, which points to its tool list and not its prompt.
Q7 Tool Design & MCP Integration

The team shares an MCP server that searches internal documentation. Every engineer should get it automatically, and each has their own access token. A new engineer reports that the assistant "doesn't have" the documentation tool. Which setup is correct, and how should it be checked?

  1. Define the server in the project's .mcp.json with one shared team token written into the file, and have each engineer confirm that the server's tools are listed.
  2. Define the server in each engineer's user-level configuration with their own token written into it, and have each engineer confirm that the server's tools are listed.
  3. Define the server in the project's .mcp.json with the token read from an environment variable, and add a line to the system prompt saying that the documentation tool is available.
  4. Define the server in the project's .mcp.json with the token read from an environment variable, and have each engineer set that variable and confirm that the server's tools are listed.
Show answer
D. The project file shares the server with everyone, and the environment variable keeps each person's token out of the repository. Checking that the tools are actually listed is how you confirm the connection. A line in the prompt can't make a tool exist.
Q8 Tool Design & MCP Integration

Two MCP tools are described as "Search documentation" and "Search code". The first covers the internal wiki and the second covers every repository. Engineers ask how an internal API should be used, and the assistant often picks the wrong tool, or falls back on the built-in Grep in the local checkout. What is the best fix?

  1. Rewrite each description to say what it searches and what it returns, and add a rule to the system prompt saying which tool to use for each kind of question.
  2. Rewrite each description to say what it searches, what input it expects, what it returns, and when to choose it over the other tool and over Grep.
  3. Merge the two tools into one search tool with a parameter for the source, and describe the parameter's allowed values briefly in the tool's input schema.
  4. Keep the descriptions as they are, and rename the tools so that each name spells out its source in full and sorts ahead of Grep in the list.
Show answer
B. The description is what the model reads when it chooses a tool, so the boundaries between similar tools belong there, including when to prefer each one. A rule in the system prompt sits apart from the tools and is easier to miss.
Q9 Tool Design & MCP Integration

Before answering questions about the platform, the assistant makes many calls to list_services and get_service_info just to find out which services exist. The catalogue holds about three hundred service descriptions and rarely changes. The same MCP server also offers actions such as restarting a service. How should the server expose these?

  1. Expose the service catalogue as MCP resources that the assistant can browse, and keep restart and similar actions as tools, each with a clear description.
  2. Expose the service catalogue and the restart actions as MCP resources, so that everything the server offers can be browsed in one consistent way.
  3. Expose the service catalogue through one tool that returns all three hundred descriptions in a single call, and keep restart and similar actions as tools.
  4. Expose each service's description through a separate tool named after that service, and keep restart and similar actions as tools, each with a clear description.
Show answer
A. Resources are for content the assistant reads, and tools are for actions it takes. A browsable catalogue removes the exploratory calls. Actions can't be resources, and three hundred tools or one enormous result would both overload the context.
Q10 Agentic Architecture & Orchestration

The assistant automates a migration across eighty modules, with a subagent handling each module. A run was interrupted after fifty. On restart it began again from the first module, and the notes that subagents had made about awkward modules were gone. What is the best design change?

  1. Have each subagent save its result and notes to a file when it finishes, and have the coordinator rerun every module on restart so that the results are consistent.
  2. Have the coordinator hold every result and note in its own conversation, summarise them every ten modules, and resume that same conversation when the run is restarted.
  3. Have the coordinator keep a manifest of completed modules, without their results or notes, and have it skip those modules when the run is restarted.
  4. Have each subagent save its result and notes to a file when it finishes, keep a manifest of completed modules, and have the coordinator read both when it restarts.
Show answer
D. Progress has to be saved outside the conversation to survive an interruption. The manifest says what is done, and the saved results and notes keep what was learned. A manifest alone avoids the repeat work but still loses the findings.
Scenario 3 Questions 11–15

Structured data extraction

You're designing a system that uses Claude to pull structured data out of documents such as invoices and contracts. The output is checked against a JSON schema and passed to downstream systems. Accuracy has to stay high, including on unusual documents.

Q11 Context Management & Reliability

About three per cent of extractions contain an error. Reviewers currently check a random ten per cent of all extractions and miss most of the errors. Analysis shows that the errors cluster in handwritten documents, in invoices with more than one currency, and in the tax ID field. Which review design is best?

  1. Route extractions to review by field-level confidence that has been checked against labelled data, and by document type, and stop the random sample now that routing covers the errors.
  2. Route extractions to review by the document-level confidence that Claude reports, without checking it against labelled data, and keep a small random sample alongside it.
  3. Route extractions to review by field-level confidence that has been checked against labelled data, and by document type, and keep a small random sample to catch what the routing misses.
  4. Raise the random sample from ten per cent to thirty per cent of all extractions, so that about three times as many of the errors are likely to be caught.
Show answer
C. Review effort should go where the errors are: weak fields and weak document types. Confidence scores only earn trust once they have been checked against known answers. The small random sample stays, because it is the only way to notice a new kind of error that the routing doesn't know about.
Q12 Prompt Engineering & Structured Output

The schema requires a purchase order number, and it requires payment terms chosen from a fixed list: net 30, net 60 or on receipt. Some invoices have no purchase order number, and some state terms such as "45 days from end of month". Claude invents purchase order numbers and files unusual terms under net 30. Which schema change is best?

  1. Make the purchase order number nullable, and add an "other" value to the payment terms with a text field for the wording, so that both gaps are recorded honestly.
  2. Make the purchase order number nullable, and keep the payment terms list as it is with an instruction to choose the closest value, so that downstream systems see known values.
  3. Keep the purchase order number required with an instruction to write "unknown" when it is missing, and add an "other" value to the payment terms with a text field.
  4. Keep both fields as they are now, and add an instruction that Claude must never invent a purchase order number or choose a payment term that isn't stated.
Show answer
A. A schema that can't express "missing" or "something else" pushes the model to make something up. A nullable field and an "other" value with the original wording give it an honest answer for each case.
Q13 Prompt Engineering & Structured Output

Some invoices have more than four hundred line items. The response is cut off part-way through, with a stop reason of max_tokens, and the JSON is invalid. The output limit has already been raised twice, and the largest invoices still fail. What is the best fix?

  1. Raise the output limit to the highest value the model allows, and retry any response that is still cut off, checking the total count against the invoice.
  2. Split the document into page ranges, extract the line items from each range in its own call, and merge the lists in code, checking the total count against the invoice.
  3. Split the document into page ranges, extract the line items from each range in its own call, and ask one final call to return all of the lists merged together.
  4. Ask Claude to return the line items in a shorter form with abbreviated field names, so that more of them fit inside the output limit of a single call.
Show answer
B. When the output is too big for one response, make the task smaller instead of the limit bigger. The merge has to happen in code: a final call that returns everything merged would hit the same limit again.
Q14 Context Management & Reliability

The system has two workloads. Accounts staff upload invoices and wait on screen for the extracted fields. Separately, an archive of two hundred thousand documents has to be processed each month, with no deadline shorter than a week. Finance wants the cost brought down. Which processing design is best?

  1. Use the Message Batches API for both workloads, since it costs less, and show staff a message that asks them to come back later for their results.
  2. Use the real-time Messages API for both workloads, since one path is simpler to run, and bring the cost down by lowering the output limit on every call.
  3. Use the Message Batches API for the uploads that staff are waiting on, since they are small, and the real-time Messages API for the monthly archive, since it is large.
  4. Use the real-time Messages API for the uploads that staff are waiting on, and the Message Batches API for the monthly archive, since it can wait and costs less.
Show answer
D. Choose by whether someone is waiting. Work that blocks a person needs a real-time call. Work that can wait hours suits batch processing, which costs less. Size isn't the deciding factor.
Q15 Prompt Engineering & Structured Output

Three teams each use a different way of getting JSON from Claude: a format described in the prompt with an example, a response that is started with an opening brace, and a tool with a JSON schema that Claude is required to call. The nightly load into the finance system rejects anything invalid, and a missing required field stops the whole load. Which approach should the extraction pipeline use?

  1. Define the schema as a tool and require the tool call, and remove the validation in code, since a required tool call can no longer return anything that is invalid.
  2. Describe the JSON format in the prompt with a full example, validate the result in code, and retry any response that fails to parse or is missing a field.
  3. Define the schema as a tool and require the tool call, validate the result in code as well, and keep prompt-only formatting for places where an occasional slip is harmless.
  4. Start Claude's response with an opening brace so that it carries on in JSON, validate the result in code, and retry any response that fails to parse.
Show answer
C. A required tool call with a schema gives the strongest guarantee on structure, which is what a strict downstream load needs. Validation in code still earns its place, because a schema can't check that the values make sense.
