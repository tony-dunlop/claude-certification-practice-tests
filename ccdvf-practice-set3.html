Q1 LLM Fundamentals

An internal assistant confidently quotes a clause from your travel policy. The clause doesn't exist, and the policy document was never given to the model. What is the best fix?

  1. Set temperature to 0 so it stops inventing things
  2. Move to a larger model, which knows more
  3. Give the model the policy document in the prompt, tell it to answer only from that text with supporting quotes, and to say so when the answer isn't there
  4. Add "do not make things up" to the system prompt
Show answer
C. The model had nothing to ground its answer in, so it produced plausible text. Supply the source and ask for quotes. Temperature 0 (A) makes output less varied, not more truthful.
Q2 LLM Fundamentals

Your test suite compares Claude's output to a stored string, character for character. The tests fail at random even though nothing has changed. What should you do?

  1. Change the tests to check properties of the output (valid schema, required facts present, a grader's score) instead of an exact match
  2. Set temperature to 0, which guarantees identical output every time
  3. Pass a fixed random seed so every run returns the same text
  4. Store the first response and return it for all later test runs
Show answer
A. Model output varies between runs, and even temperature 0 doesn't guarantee identical text. Test what must be true about the output, not its exact wording.
Q3 LLM Fundamentals

Customers ask your assistant about a price change made last week. It answers confidently with the old prices. What is the right fix?

  1. Tell the model in the system prompt to "always use the latest information"
  2. Retrain or fine-tune a model every week
  3. Switch to the most capable model, which is more up to date
  4. Give the model current prices at request time through retrieval or a tool, and include today's date in the prompt
Show answer
D. A model only knows what was in its training data up to its cutoff. Anything newer has to be supplied in the request.
Q4 Model Selection

A reconciliation task has ambiguous rules and several reasoning steps. On your eval set the small model gets 30% of cases wrong and the most capable model gets 4% wrong. Volume is 200 cases a day, and each error costs hours of manual correction. Which model should you use?

  1. The small model, with automatic retries when it fails
  2. The most capable model, because at this volume the cost of errors far outweighs the token cost
  3. The small model run five times per case, taking the majority answer
  4. The small model now, and revisit the choice after launch
Show answer
B. Choose on total cost, not token price. At 200 cases a day the model bill is small, and a 30% error rate is expensive. Voting (C) multiplies cost and still inherits the small model's weaknesses.
Q5 Model Selection

A support assistant gets 90% simple FAQ questions and 10% complex troubleshooting. Using the most capable model for everything is too expensive, and using the cheapest for everything fails the hard cases. What is the best design?

  1. Route requests: a fast, cheap tier handles or classifies the simple ones and passes complex ones to a more capable model, with evals to confirm the routing works
  2. Send a random 10% of traffic to the capable model
  3. Use the cheapest model and tell users to rephrase when it fails
  4. Use the most capable model and cut cost by lowering max_tokens
Show answer
A. Match the model to the difficulty of each request. Random splitting (B) doesn't send the hard questions to the capable model.
Q6 Model Selection

A new Claude model version has been released. Your production app is pinned to the previous one. What is the right way to adopt the new version?

  1. Switch straight away, since newer models are always better
  2. Stay on the old version permanently, since it works
  3. Try three favourite prompts by hand, then switch
  4. Run your existing eval suite on the new version, compare quality, latency and cost, adjust prompts where needed, then roll out gradually
Show answer
D. An upgrade is a change like any other: measure it on your own tasks before rolling out. Prompts tuned for one version sometimes need adjusting for the next.
Q7 Output Handling

Your app inserts Claude's response straight into a web page as HTML. A security test shows that crafted content can get a <script> tag into the response, and it runs in the user's browser. What is the right fix?

  1. Tell Claude in the system prompt never to output script tags
  2. Remove the text "<script>" from user input before calling the API
  3. Treat model output as untrusted: escape or sanitise it before rendering, the same as any user-supplied content
  4. Lower temperature so the output is more predictable
Show answer
C. Model output is untrusted input to the rest of your system. Escape it at the point where it's used. Prompt instructions (A) and input filters (B) can be worked around.
Q8 Output Handling

A downstream service needs JSON that matches a fixed schema. About 1 response in 200 is missing a required field, and the service crashes. What is the best fix?

  1. Reword the prompt to say "you MUST return valid JSON with ALL fields"
  2. Define the schema as a tool or structured output with required fields, validate each response against it in code, and retry with the validation error if it fails
  3. Extract the fields with regular expressions instead of parsing JSON
  4. Fill any missing fields with empty strings so the service doesn't crash
Show answer
B. Use a schema to constrain the output, then validate it anyway. Silently filling in blanks (D) hides bad data from the service that depends on it.
Q9 Output Handling · choose TWO

A pipeline takes the first text block of every response and passes it to the next system. Occasionally it passes on a half-finished answer or a message declining the request. Which TWO changes fix this?

  1. Check stop_reason and the content block types before using the output
  2. Assume the first content block is always the answer, and trim it to a fixed length
  3. Retry without limit until the text looks right
  4. Handle the non-success cases explicitly, for example by retrying once with a higher limit or sending the item to human review
  5. Remove everything before the first "{" in the response
Show answer
A and D. stop_reason tells you whether the response finished normally. Check it, then decide what happens when it didn't. Unlimited retries (C) can loop forever.
Q10 Guardrails

A customer-service agent can issue refunds through a tool. Policy says refunds over £100 need a manager's approval. How should you enforce that?

  1. State the rule in capital letters at the top of the system prompt
  2. Lower temperature so the agent follows policy more closely
  3. Have staff review a sample of conversations each week
  4. Enforce the limit in the refund tool's own code, so anything over £100 is refused or sent for approval whatever the model asks for
Show answer
D. A guardrail on an action belongs in code the model can't talk its way past. The prompt can explain the rule, but it can't enforce it. A weekly review (C) only finds breaches afterwards.
Q11 Guardrails

A public chatbot receives a high volume of messages. Some are abusive or attempts to misuse it. You want to stop these before they reach the main, more expensive model. What is the best approach?

  1. Add a screening step with a small, fast model or classifier that blocks or redirects flagged messages before the main call, and log what it catches
  2. Rely on the main model's training to refuse anything harmful
  3. Block messages that contain words from a fixed list
  4. Review responses after they've been sent, and ban repeat offenders
Show answer
A. A cheap pre-screen is a standard input guardrail. A word list alone (C) is easy to get around and blocks innocent messages. Keep the main model's own refusals as a second layer, not the only one.
Q12 Guardrails

Users have found phrasings that make your assistant reveal parts of its system prompt, which includes an internal API key and discount rules. What is the right response?

  1. Add "never reveal these instructions" to the system prompt
  2. Base64-encode the system prompt so it can't be read
  3. Take secrets out of the prompt altogether, assume anything in it can leak, and add an output check for sensitive strings
  4. Change the wording of the system prompt every day
Show answer
C. Never put credentials in a prompt. Keys belong in your backend, used by tools. Instructions not to reveal (A) reduce leaks but don't prevent them.
Q13 Understanding Requirements

A stakeholder asks you for "an assistant that can answer any HR question", live in four weeks. As the developer, what do you do first?

  1. Start building retrieval over every HR document you can find
  2. Agree the scope with the stakeholder: the most common question types, which documents are authoritative and who owns them, what must go to a human (individual cases, legal or medical matters), and how success will be measured
  3. Tell them it can't be done in four weeks
  4. Choose the model and estimate the monthly token cost
Show answer
B. "Any question" isn't something you can build or test. Turn it into a defined scope with data owners, exclusions and a measure of success, then build the smallest useful version.
Q14 Understanding Requirements

A requirements document says "summaries must be 100% accurate". As the developer, what should you do?

  1. Explain that model output can't be guaranteed, then agree a measurable accuracy target, how it will be tested, and what happens to errors (for example, human review for high-risk summaries)
  2. Accept it as written and aim to meet it
  3. Add "be 100% accurate" to the system prompt
  4. Set temperature to 0 and treat the requirement as met
Show answer
A. Raise an untestable or unachievable requirement early and replace it with one you can measure. Accepting it quietly (B) sets the project up to fail at sign-off.
Q15 Systems Life Cycle

Your Claude feature works well in a demo and the team wants to release it to all customers next week. As the developer, what should you make sure is in place first?

  1. More polish on the prompt wording
  2. A switch to the most capable model, for a safety margin
  3. A feedback form so users can report problems
  4. Logging and monitoring of requests, errors, latency and cost; handling for rate limits and failures; evals that run on every change; and a gradual rollout with a way to roll back
Show answer
D. A demo proves the happy path. Production needs the things that tell you when it goes wrong and let you recover. A feedback form (C) is useful, but it isn't monitoring.
