Scenario 1 Questions 1–5

Customer support resolution agent

You're designing an agent that resolves support tickets for an online retailer. It has tools to look up customers and orders, issue refunds, and escalate to a human. The target is to resolve 80% of tickets at first contact without a person stepping in.

Q1 Agentic Architecture & Orchestration

In testing, the agent sometimes issues a refund before it has confirmed who the customer is. The system prompt already says to verify identity first. What is the best architectural fix?

  1. Move the verification instruction to the top of the system prompt, and mark it there as a critical rule
  2. Add few-shot examples to the prompt that show identity verification happening before any refund is issued
  3. Add a gate in code, so the refund tool is refused unless the session has a verified customer ID
  4. Have a second model review each finished conversation, and flag any where verification was skipped before a refund
Show answer
C. When a step must always happen first, enforce the order in code. Prompt instructions and examples (A, B) make it more likely but can't guarantee it, and a review afterwards (D) only finds the mistake once the money has gone.
Q2 Tool Design & MCP Integration

When the order system is briefly unavailable, the lookup tool returns the text "Operation failed". The agent then either retries many times or tells the customer the order doesn't exist. How should the tool be redesigned?

  1. Return a structured error giving the kind of failure, whether a retry makes sense, and a short explanation
  2. Return an empty result whenever the order system is unavailable, so the agent moves on to its next step
  3. Retry inside the tool until the order system responds, so the agent never has to see a failure
  4. Add a line to the system prompt telling the agent to retry three times after any tool failure
Show answer
A. The agent can only respond sensibly if it can tell a temporary outage from "not found". Give it the category and whether to retry. An empty result (B) looks the same as a real "no such order".
Q3 Agentic Architecture & Orchestration

You need to decide when the agent hands a ticket to a human. Which rule is the most reliable?

  1. Escalate when a sentiment score on the customer's messages shows that they are upset or frustrated
  2. Escalate when the customer asks for a person, policy doesn't cover it, or the agent is stuck
  3. Escalate when the agent rates its own confidence in resolving the ticket at below seventy per cent
  4. Escalate any conversation that goes past five turns without the ticket being marked as resolved
Show answer
B. Clear, checkable conditions work best. An upset customer may have a simple problem the agent can fix, and a model's rating of its own confidence (C) isn't a dependable signal.
Q4 Context Management & Reliability

In long conversations the history is summarised to save space. Afterwards, the agent refers to "your recent order" and has lost the order number and the refund amount the customer gave earlier. What is the best fix?

  1. Stop summarising altogether, and keep the whole conversation history in every request sent to the model
  2. Have the agent ask the customer to repeat the order number and amount whenever they're needed
  3. Tell the summariser to write longer summaries that try to keep more of the conversation's detail
  4. Keep order numbers, amounts and dates in a separate block that is always sent, never summarised
Show answer
D. Summaries lose exact values. Keep the facts that must stay precise in their own block, outside the part that gets compressed. Keeping everything (A) only delays the problem.
Q5 Prompt Engineering & Structured Output

When the agent escalates, the human agent can't see the conversation. What should the handoff contain?

  1. A structured summary: customer ID, the issue, findings, actions already taken, and a recommended next step
  2. The full raw transcript of the conversation, including every tool call and tool result along the way
  3. A one-line note saying the customer needs help, plus a link to the customer's account page
  4. The customer's sentiment score, the number of turns so far, and the time the conversation started
Show answer
A. The person picking it up needs enough to act without re-asking the customer. A raw transcript (B) makes them dig for it, and one line (C) makes them start again.
Scenario 2 Questions 6–10

Multi-agent research system

You're designing a research system in which a coordinator agent hands work to specialised subagents: one searches the web, one analyses documents, one combines the findings and one writes the report. Each subagent runs with its own separate context.

Q6 Agentic Architecture & Orchestration

The coordinator calls the synthesis subagent with the instruction "synthesise the findings". What comes back is generic and ignores what the search and analysis subagents found. What is the most likely cause?

  1. The synthesis subagent is running on a model that isn't capable enough to combine findings from several sources
  2. Subagents can't see the coordinator's conversation, so the findings must be passed explicitly in the subagent's instructions
  3. The synthesis subagent's system prompt is too short to explain how findings should be combined into a summary
  4. The search subagent returned its results in a format that the synthesis subagent wasn't able to read
Show answer
B. A subagent starts with only what it's given. Anything it needs (the findings, the goal, the output format) has to be in the task the coordinator hands over.
Q7 Agentic Architecture & Orchestration

The coordinator sends five independent research questions to the search subagent one after another, waiting for each to finish. A run takes 12 minutes. What is the best way to speed it up?

  1. Have the coordinator start all five subagent tasks in the same turn, so that they run in parallel
  2. Put all five questions into a single subagent task, so that only one subagent has to start
  3. Switch the search subagent to a smaller, faster model, so that each of the five searches finishes sooner
  4. Limit each search to its top two results, so that every subagent has less material to read
Show answer
A. Independent tasks can run side by side. One combined task (B) fills a single context with five topics, and the cuts in C and D trade away quality.
Q8 Context Management & Reliability

The web-search subagent times out part-way through a task. How should that failure be handled?

  1. The subagent returns an empty result marked as successful, so the rest of the workflow carries on
  2. The whole research run stops with an error, and the user is asked to start it again
  3. The subagent keeps retrying the search on its own, for as long as it takes to succeed
  4. The subagent reports the failure and any partial results to the coordinator, which decides what happens next
Show answer
D. Send enough detail up for the coordinator to choose: retry, use another source, or carry on and note the gap. Hiding the failure (A) produces a report with a silent hole in it.
Q9 Context Management & Reliability

The final report gives statistics with no sources, and in one place it quietly picks one of two conflicting figures. What change fixes this at the design level?

  1. Tell the report writer to add a list of citations at the end of every report it produces
  2. Have subagents return findings as claim-and-source pairs, kept through synthesis, with conflicts flagged and not resolved silently
  3. Use a more capable model for the report writer, so that it attributes statistics to sources more reliably
  4. Run the search step twice for every question, and keep only the figures that match in both runs
Show answer
B. Source details are lost at each handoff unless they're carried as data. The report writer (A) can't cite what it was never given.
Q10 Tool Design & MCP Integration

Every subagent has been given the full set of 18 tools. The document-analysis subagent sometimes wanders off to run web searches, and tool selection has become less accurate across the system. What is the best fix?

  1. Add a line to each subagent's prompt that lists the tools it has but shouldn't use
  2. Write longer, more detailed descriptions for all 18 tools, so each subagent can tell them apart
  3. Give each subagent only the tools its own role needs, and remove the rest from its set
  4. Have the coordinator choose the tool for every step, and tell each subagent which one to call
Show answer
C. Fewer, role-specific tools make selection more reliable and keep each subagent on its job. Asking it not to use tools it can see (A) is weaker than not offering them.
Scenario 3 Questions 11–15

Claude Code for continuous integration

Your team is adding Claude Code to its CI pipeline. On every pull request it will review the changes and post comments, and a nightly job will generate missing tests.

Q11 Claude Code Configuration & Workflows

The CI job needs Claude Code's review findings in a form a script can read, so each finding can be posted as an inline comment on the right file and line. What is the best approach?

  1. Run it in interactive mode, and have the script copy the findings from the terminal output afterwards
  2. Run it in non-interactive mode (-p) with JSON output and a defined structure for each finding
  3. Ask for the review as Markdown, and have the script extract each finding with regular expressions
  4. Have Claude Code write its findings into CLAUDE.md, and have the script read them from there
Show answer
B. Automation needs non-interactive mode and structured output it can parse. Scraping free text (C) breaks whenever the wording changes.
Q12 Claude Code Configuration & Workflows

In the nightly job, the same Claude Code session that writes new tests is then asked to review them. It almost never finds a problem. What is the best change?

  1. Ask the same session to review the tests a second time before the job finishes
  2. Add an instruction to the review step that tells the session to be more critical
  3. Run the review in a separate session that doesn't have the writing session's context
  4. Use a more capable model tier for the review step than for the writing step
Show answer
C. A session that made the decisions tends to agree with them. A fresh session judges the result without the reasoning that produced it.
Q13 Prompt Engineering & Structured Output

The review bot posts many comments about style and minor preferences. Developers have started ignoring all of them, including the real bugs. What is the best fix to the review prompt?

  1. Add an instruction to report only the issues that the bot is highly confident about
  2. Add an instruction to be conservative, and to avoid commenting unless it is really necessary
  3. Limit the bot to three comments on each pull request, whatever it finds in the changes
  4. Say what to report (bugs, security problems) and what to skip (style, naming), with examples
Show answer
D. Specific categories and examples change what gets reported. Vague instructions such as "be conservative" (A, B) don't tell the model where the line is.
Q14 Claude Code Configuration & Workflows

The CI job ignores the team's testing conventions. On one developer's machine Claude Code follows them, because they wrote the conventions into their personal ~/.claude/CLAUDE.md. What is the right fix?

  1. Copy that developer's personal CLAUDE.md onto the CI machine, so the job picks it up
  2. Paste the conventions into the CI job's prompt, so they're sent with every review request
  3. Ask every developer to add the same conventions to their own personal CLAUDE.md file
  4. Put the conventions in the project's CLAUDE.md, committed to the repository for CI and every developer
Show answer
D. Personal settings apply to one person's machine. Team conventions belong in the project file, under version control, where every environment picks them up.
Q15 Prompt Engineering & Structured Output

On a pull request that touches 40 files, a single review pass gives detailed comments on the first few files, thin ones on the rest, and misses a bug caused by two files changing together. What is the best redesign?

  1. Review each file in its own pass, then run a separate pass on how the changes interact
  2. Keep the single pass, and ask for a longer and more thorough review of all forty files
  3. Keep the single pass, and use a model with a larger context window to hold every file
  4. Ask developers to keep every pull request under ten files, so a single pass is enough
Show answer
A. Attention spreads thin over a large single pass. Split the work so each file gets full attention, and give cross-file problems their own pass.
