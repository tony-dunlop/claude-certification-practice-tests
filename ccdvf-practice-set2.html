Q1 Applications & Integration

You send Claude four scanned invoice pages as images in one request and ask it to compare totals. Its answers mix up which figure came from which page. What is the best fix?

  1. Stitch all four pages into one tall image so there's only one input
  2. Label each image in text before it ("Invoice 1:", "Invoice 2:" and so on), and put the images before the question
  3. Send each page in a separate API call and concatenate the four answers
  4. Switch from URL image sources to base64 so the model reads them more accurately
Show answer
B. Anthropic's vision guidance is to label multiple images and to put images before the text that asks about them. Separate calls (C) lose the cross-page comparison, and the encoding (D) doesn't affect understanding.
Q2 Applications & Integration

A prompt change caused a quality regression in production. The prompts are edited as inline strings in several services, and nobody can tell which prompt version produced which logged output. What is the best long-term fix?

  1. Move the prompts to a database that product managers can edit live
  2. Add today's date to the top of each prompt so outputs can be traced
  3. Freeze all prompts and stop changing them
  4. Version the prompts in source control, log the prompt version and model ID with every request, and run evals in CI whenever a prompt changes
Show answer
D. Treat prompts like code: versioned, traceable in logs, and tested before release. Live editing with no history (A) makes the tracing problem worse.
Q3 Applications & Integration

Before sending large document requests, your service needs to check that each one fits in the context window and to estimate its input cost. What is the most reliable way to do this?

  1. Call the API's token counting endpoint with the same messages, system prompt and tools
  2. Estimate tokens as characters ÷ 4
  3. Send the request and catch the error if it's too long
  4. Count tokens with an open-source tokenizer from another model provider
Show answer
A. The token counting endpoint uses Claude's own tokenizer and includes tools, images and the system prompt. A characters ÷ 4 rule (B) is a rough guess, and another provider's tokenizer (D) counts differently.
Q4 Applications & Integration

A director asks your team to "use Claude to cut support costs." What should you do first?

  1. Prototype with the most capable model straight away, to show value quickly
  2. Design a multi-agent architecture that can handle every ticket type
  3. Turn the goal into measurable requirements: which ticket types, what counts as success, when to hand over to a human, and the latency, privacy and data-residency constraints
  4. Write the system prompt, since prompt quality decides everything else
Show answer
C. This is the "Understanding requirements" skill: business goal → functional and infrastructure requirements. Building before you know what success means is the trap in A, B and D.
Q5 Model Selection & Optimization

You're adding inline code completion to an editor. Suggestions must start appearing in well under a second, and most completions are short. Which setup fits best?

  1. The most capable model with extended thinking, for the best suggestions
  2. The Message Batches API, to keep costs down
  3. A larger model, warmed up with a dummy request every minute
  4. A fast, small model tier with streaming, a low max_tokens, and caching for the stable part of the prompt
Show answer
D. For latency, choose a small tier, stream the output, cap its length and cache the stable prefix (caching cuts latency as well as cost). Thinking (A) and batches (B) both add delay.
Q6 Model Selection & Optimization

A ticket-routing classifier has extended thinking turned on. It's slow and expensive, and on your eval set its accuracy is the same with thinking turned off. What should you do?

  1. Raise budget_tokens so the thinking is more thorough
  2. Turn thinking off for this task, and keep it for problems that need multi-step reasoning
  3. Move the classifier to the Batches API, keeping thinking on
  4. Switch to a larger model and keep thinking on
Show answer
B. The eval data shows thinking adds cost and delay without improving accuracy. Spend it only where it measurably helps.
Q7 Agents & Workflows

You're building an agent with the Claude Agent SDK. It must read anywhere in the repo, but it may only write files under /output. What is the most reliable way to enforce that?

  1. Limit the agent's allowed tools, and use a permission callback or PreToolUse hook that denies any write outside /output
  2. State the rule clearly in the system prompt
  3. Run the agent with full permissions so it doesn't stall on prompts, and review the diff afterwards
  4. Remove all write tools from the agent
Show answer
A. Enforce it in code, not in the prompt. B is only a request. D can't meet the requirement to write to /output.
Q8 Agents & Workflows · choose TWO

A custom agent loop sometimes gets stuck calling the same tool with the same arguments over and over, until it's stopped by hand. Which TWO safeguards should you add?

  1. A hard cap on turns, tokens or cost per task, with a clean failure when it's reached
  2. Drop the tool_result from the history when a call repeats, so the model can't see the loop
  3. Detect repeated identical calls, and return a tool result that explains the problem so the model can change course
  4. Raise max_tokens so the agent can finish its reasoning
  5. Set temperature to 0, which removes loops
Show answer
A and C. A budget cap is the backstop, and a useful tool result helps the model recover. Dropping results (B) breaks the tool-use protocol and hides the information the model needs.
Q9 Prompt & Context Engineering

Your system prompt says "Do not use markdown." The output still often contains bullet lists and bold headings. The system prompt itself is written in heavy markdown. What is the best fix?

  1. Repeat "NO MARKDOWN" several times in capital letters
  2. Leave the prompt alone and strip the markdown with a regex afterwards
  3. Raise temperature to break the formatting habit
  4. Describe what you want instead (for example, "write in flowing prose paragraphs"), and remove the markdown from the prompt itself
Show answer
D. Anthropic's guidance: say what to do rather than what not to do, and match the style of the prompt to the output you want. A heavily formatted prompt pulls the output towards the same formatting.
Q10 Prompt & Context Engineering

You want Claude to reason step by step to improve accuracy, but your code must extract the final answer reliably. What is the best prompt design?

  1. Ask for the final answer only, to keep parsing simple
  2. Ask for reasoning, then take the last line of the response as the answer
  3. Ask for the reasoning inside <thinking> tags and the final answer inside <answer> tags, then parse the answer tag
  4. Make one call for the reasoning and a separate call for the answer, without passing the reasoning between them
Show answer
C. XML tags separate the reasoning from the answer so it can be parsed reliably. Asking for the answer only (A) gives up the accuracy gain, the last line (B) is fragile, and D throws the reasoning away.
Q11 Tools & MCP

You're building an MCP server for an HR system. It must provide a set of read-only policy documents for applications to attach as context, and it must also let the model submit leave requests. How should you expose these?

  1. Make every policy document its own tool
  2. Expose the policy documents as MCP resources and leave submission as an MCP tool
  3. Expose both as MCP prompts
  4. Hard-code the documents into the server's instructions text and expose leave submission as a tool
Show answer
B. In MCP, resources are context the application chooses to attach, tools are actions the model calls, and prompts are reusable templates the user chooses. Match each one to its job.
Q12 Tools & MCP

A get_account tool returns the full 200 KB account record, and after a few calls the agent's context is full. What is the best fix?

  1. Redesign the tool to return only the fields the task needs, with filter or pagination parameters and concise errors
  2. Move to a model with a larger context window
  3. Cut the response off at 4,000 characters, even if that's mid-JSON
  4. Pass every tool result through a second LLM call that summarises it
Show answer
A. Design tool outputs for the model: return what it needs and let it ask for more. Cutting mid-JSON (C) corrupts the data, and an extra summarising call (D) adds cost and delay on every call.
Q13 Security & Safety

The support transcripts you send to Claude sometimes contain full card numbers. Compliance requires that card numbers never leave your environment. What should you do?

  1. Tell Claude in the system prompt to ignore any card numbers
  2. Ask Claude to redact card numbers from its output
  3. Use the smallest model tier, since it keeps less of what it sees
  4. Detect and redact (or tokenise) card numbers in your own code before the API call
Show answer
D. A, B and C all still send the card numbers to the API. The only way to keep them in your environment is to remove them before the request leaves.
Q14 Eval, Testing & Debugging

You've rewritten a summarisation prompt and believe it's better. How should you confirm that before shipping it?

  1. Ship it and watch user complaints for a week
  2. Try five examples by hand and compare the outputs
  3. Run the old and new prompts on the same fixed eval set, with defined graders (code checks where possible, and an LLM judge using a rubric checked against human labels), and compare the scores
  4. Ask Claude which of the two prompts is better
Show answer
C. Use a fixed dataset, graders you've validated and a side-by-side comparison. Five examples (B) are anecdotes, and asking the model which prompt is better (D) isn't measurement.
Q15 Claude Code

Your team has a detailed 30-step release procedure with helper scripts, used about once a fortnight. Keeping it in the project's CLAUDE.md bloats every session's context. What is the best home for it?

  1. Leave it in CLAUDE.md so it's always available
  2. Package it as a Skill (a SKILL.md with a clear description, plus the scripts), so it's loaded only when relevant. Distribute it as a plugin if other repos need it
  3. Move it into .claude/settings.json
  4. Keep it in a wiki and paste it into the chat at each release
Show answer
B. Only a skill's description is loaded until the task calls for it, so the full procedure stays out of context until it's needed. settings.json (C) holds configuration, not instructions.
